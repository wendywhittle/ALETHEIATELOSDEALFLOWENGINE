ALETHEIATELOS DEALFLOW ENGINE

Architecture

The DealFlow Engine is a lean application for acquiring, underwriting, recording, and reviewing real-estate deals.

The architecture exists to support one reliable loop:

PUBLIC USER
    ↓
DEAL INTAKE
    ↓
VALIDATION
    ↓
CANONICAL DEAL RECORD
    ↓
UNDERWRITING ENGINE
    ↓
USER RESULTS
    ↓
EXCEL ARTIFACT
    ↓
INTERNAL DEAL PIPELINE
    ↓
DEAL REVIEW

The system should remain as small as possible while supporting this loop reliably.

2. Source of Truth

The Deal Record is the canonical source of truth.

The application owns the authoritative deal data.

The underwriting engine derives calculations from that data.

The Excel workbook is generated from the Deal Record and underwriting results.

Therefore:

DEAL RECORD
    ↓
UNDERWRITING
    ↓
EXCEL

Never:

EXCEL
    ↓
APPLICATION STATE

The Excel workbook must not become a competing database or source of truth.

⸻

Deal
├── identity

│   ├── name
│   ├── asset_type
│   └── location
│
├── original_inputs
│   ├── purchase_price
│   ├── noi
│   ├── egi
│   ├── operating_expenses
│   ├── occupancy
│   ├── ltv
│   ├── interest_rate
│   ├── amortization_years
│   ├── hold_period
│   ├── exit_cap_rate
│   └── closing_costs
│
├── underwriting
│   ├── derived_noi
│   ├── cap_rate
│   ├── loan_amount
│   ├── initial_equity
│   ├── debt_service
│   ├── dscr
│   ├── cash_flow

Original inputs remain identifiable as original inputs.

Derived values remain identifiable as derived values.

Missing information remains explicit.

⸻

4. Deal ID

Every submitted deal receives a unique identifier.

Example:

AT-2026-000001
AT-2026-000002
AT-2026-000003

The Deal ID must be generated by the application.

It must never depend on the property name, address, or purchase price.

⸻

5. Underwriting Engine

The underwriting engine is a pure calculation layer.

Conceptually:

underwriting = calculate(deal_inputs)

The calculation layer should:

* accept structured inputs
* perform deterministic calculations
* return structured outputs
* never modify the original inputs
* never invent missing information
* never make investment decisions

Example:

purchase_price = $10,000,000
NOI = $650,000
cap_rate = NOI / purchase_price
cap_rate = 6.50%

If NOI is not supplied:

NOI = EGI - Operating Expenses

only when both values are actually available.

If a calculation cannot be performed:

status = unavailable

not:

value = 0

⸻

6. Calculation Provenance

Every derived metric should be traceable to the inputs that produced it.

For example:

{
  "metric": "cap_rate",
  "value": 0.065,
  "status": "calculated",
  "inputs": [
    "purchase_price",
    "noi"
  ]
}

This makes the calculation layer inspectable and testable.

⸻

7. Missing Information

Missing data is a valid state.

The application must distinguish between:

SUPPLIED
CALCULATED
UNAVAILABLE
UNKNOWN

Do not silently convert:

missing interest rate

into:

0%

Do not silently convert:

missing financing

into:

all cash

unless the user explicitly supplied those values.

⸻

8. Pipeline

The internal pipeline is intentionally simple.

NEW
 ↓
REVIEWING
 ↓
PURSUЕ
 / \
HOLD PASS

The pipeline represents workflow state.

It does not represent an investment decision made by the software.

A human controls status changes.

⸻

9. Excel Artifact

The Excel generator consumes canonical deal information.

Conceptually:

workbook = generate_excel(deal_record, underwriting_result)

The generated workbook should contain:

Deal Summary
Operating Inputs
Financing
Returns
Assumptions / Missing Data

The workbook is an artifact.

It is not authoritative application state.

⸻

10. Persistence

The first implementation should use a simple persistent database.

A relational database is preferred because the core data is structured and transactional.

The initial model should remain small.

A reasonable starting point is:

deals

with additional tables only when a genuine requirement exists.

Do not create a complex domain model before the product requires one.

⸻

11. Application Boundaries

The application should maintain clear boundaries between:

WEB UI
    ↓
APPLICATION/API
    ↓
DEAL RECORD
    ↓
UNDERWRITING
    ↓
ARTIFACT GENERATION

The UI should not perform authoritative underwriting calculations independently of the backend.

The Excel generator should not maintain independent business logic.

The database should not contain duplicated calculated versions of the same deal unless required for persistence or auditability.

⸻

12. Validation

Validation occurs before a Deal Record is accepted.

Validation should distinguish:

required field missing
optional field missing
invalid value
valid value

Examples of invalid input include:

purchase_price < 0
NOI < 0
LTV < 0
LTV > 100%
interest_rate < 0
amortization_years <= 0

Validation errors should be explicit and understandable.

⸻

13. Security Boundary

The DealFlow Engine is an analytical and administrative system.

It does not have authority to:

execute purchases
execute trades
move capital
transfer funds
access brokerage accounts
mutate portfolios
authorize investments autonomously

The system produces analysis.

Humans make decisions.

⸻

14. What This Architecture Does NOT Include

The initial system intentionally does not include:

* autonomous investment agents
* multi-agent orchestration
* Computational Kaleidoscope
* Epistemic Memory
* Decision Gates
* portfolio mutation
* brokerage integrations
* trading infrastructure
* capital-transfer infrastructure
* speculative event buses
* unnecessary microservices
* unnecessary queues
* unnecessary workers
* decorative intelligence dashboards
* fake AI activity

Those are not required to make DealFlow Engine useful.

⸻

15. Design Rule

The architecture should follow one rule:

Keep the architecture boring. Make the workflow real.

A real deal entering the system and successfully becoming:

DEAL
→ UNDERWRITING
→ RESULT
→ EXCEL
→ PIPELINE
→ REVIEW

is more important than architectural complexity.

⸻

16. Definition of Architectural Success

The architecture is successful when a real submission can traverse the complete system without duplicated state, hidden assumptions, fabricated numbers, or manual reconstruction.

VISITOR
  ↓
DEAL
  ↓
VALIDATION
  ↓
CANONICAL RECORD
  ↓
UNDERWRITING
  ↓
RESULT
  ↓
EXCEL
  ↓
PIPELINE
  ↓
HUMAN REVIEW

That is the system.

Everything else is secondary.
